The idea

KeyRotator sits between your code and an API. Your code sends its requests to KeyRotator instead of the API. KeyRotator adds one of your keys, forwards the request, and passes the answer back unchanged, streaming included.

your code  ──►  KeyRotator (127.0.0.1:8787)  ──►  the API
                    adds the next key
                    retries with another key if one fails

Your code never needs a real key. The keys live in one place, and you can add, rest or remove them without touching any code.

Providers

A provider is one API you call, such as OpenAI. It has:

  • Base URL: the API's address, for example https://api.openai.com/v1.
  • Proxy URL: the address your code uses instead, shown on the provider card with a Copy URL button. A request to …/p/<id>/chat/completions goes to <base URL>/chat/completions.
  • Keys, a rotation mode, and the places the key is sent, all explained below.

Switching a provider off makes its proxy URL answer 404 until you switch it back on.

Keys and aliases

Each key has an alias, a short name such as billing. A key added without one is called key 1, key 2 and so on, using the lowest free number. Aliases are unique within a provider, ignoring upper and lower case.

Most keys are a single value. Some APIs need a matched set of values instead, such as an API key and the session id that goes with it. A key can hold those too: see Matched pairs.

Rotation modes

The rotation mode decides which key the next request uses. With three keys, a, b and c:

ModeRequests 1 to 6 useGood for
Round robina, b, c, a, b, cSpreading load evenly. The order repeats from the first key.
Randomb, a, a, c, b, aNo pattern at all. Even over time, uneven in the short run.
Least useda, b, c, a, b, cGiving every key the longest rest. Starts with the key that has waited longest.

Only usable keys take part: a switched-off key is skipped, and so is a resting or rejected one (see below). Open Preview on a provider card, or look at the bottom of the edit form, and use Prev and Next to see exactly which key each request uses. Nothing is sent while you preview.

When a key fails

The API answersKeyRotator
429, any 5xx, or no answerThe key rests (shown as Resting) for the time the API asks for in Retry-After, or for the cooldown in Settings, 60 seconds by default. The request is retried with another key.
401 or 403The key is marked Rejected and set aside. The request is retried with another key.
anything else, including 400The answer goes straight back to your code. The key stays healthy.

A request tries up to Max retries keys (Settings, 3 by default). If every key is resting, a resting key is used anyway rather than failing outright.

The health check path is a cheap GET path on the API, such as /models. KeyRotator calls it with a key to test it: when you press Test, and every 90 seconds for keys whose rest is over and for keys marked Rejected. A key that passes becomes healthy again on its own. Reset clears a key's state by hand.

Where the key goes

APIs expect the key in different places. Under Where your API key is sent, each row is one place:

  • Where: a request header, or a parameter in the URL.
  • Name: the header or parameter name, such as Authorization or api_key.
  • Prefix: text written just before the value. Bearer (with its space) is the most common.
  • Sends: which value of the key goes here. For a normal key that is key.

The line under each row shows exactly what it adds, for example → Authorization: Bearer ‹key›. The Add a place buttons fill in the common ones. Every place on a request uses the same key. If your code sends a value for one of these headers or parameters itself, KeyRotator replaces it.

Matched pairs

Some APIs only accept values that belong together: an API key and the session id issued with it, an app id and its secret, an access key and its secret key. Sending key 1 with key 2's session id fails.

For that, a key can have parts next to its main value. Each key holds its own matched set:

Aliaskeysession_id
acct-1AAA…111…
acct-2BBB…222…

Then add one place per value. For example, ?api_key= sending key, and a header x-session-id sending session_id (pick + New part in the Sends column to name it). Any mix of headers and URL parameters works.

Rotation picks one whole key, so every request gets a matching set: acct-1's key with acct-1's session id, never acct-2's. This holds for round robin, random and least used alike. Once a place sends a part, the add-key bar asks for it, and the key table shows which parts each key has. A key without a part that is needed is skipped, and marked no session_id in red, until you edit it. If a request fails, only the key it used is marked.

Fixed values

Some APIs also want a header that never changes, such as anthropic-version: 2023-06-01. Add it under Fixed values and it is sent on every request.

Groups of fixed values

Fixed values with no group are independent: each one is sent whenever it is switched on. Fixed values in the same group are switched as one: if any of them is off, none of them is sent, and their rows say so. That is handy for a set of headers you turn on and off together, such as beta-feature headers while you try something out.

Pick + New group in the Group column to start a group, then choose the same group on the other rows. Groups do not decide which values travel together on a request; for that, see Matched pairs.

Rate limits

Two limits, both in requests per second, keep you under an API's quota:

  • Rate limit: all traffic to one provider, across its keys. Requests over the limit get a 429 at once, with a Retry-After header.
  • Per-key rate: traffic through any single key. A key at its limit is skipped and another key is used. Only when every key is at its limit does the request get a 429.

Settings holds the default for every provider. On a provider, "same as Settings" (a blank field) means it uses that default; a number overrides it for this provider only; 0 means no limit. A limit of 5 allows a burst of 5 requests at once, then one every 200 ms. Being throttled by KeyRotator never counts against a key.

Tokens

  • Proxy token: a password for the proxy URLs. Clients must include it, so someone who only has the URL cannot use your keys. The URL shown on the card already contains it. Set one in Settings for all providers, or on a provider to override it. It is removed before the request reaches the API.
  • Admin token: protects the /api endpoints that the dashboard, CLI and TUI use, and /metrics. The dashboard asks for it once and remembers it.

KeyRotator only listens on 127.0.0.1 unless you change it. Set both tokens before opening the port to other machines; KeyRotator warns at startup if you don't.

Pinning a key

Every answer says which key served it, in the X-Rotator-Key header (with X-Rotator-Key-Id and X-Rotator-Provider). To use one key on purpose, send X-Rotator-Key: billing, with an alias or id. A pinned key skips its per-key rate limit but still counts toward the provider's.

Keeping it running

  • Your settings, keys, their counts and the Activity log are saved, so they survive restarts and updates. The Activity log lives in activity.json next to the config.
  • keyrotator start runs it in the background, so it keeps going after you close the terminal. keyrotator stop and keyrotator status do what they say.
  • Start at login in Settings starts it whenever you sign in, on Windows, macOS and Linux.
  • It also runs as a Windows service, as a systemd service, or in Docker.
  • keyrotator tui opens a full-screen dashboard in the terminal, and keyrotator help lists every command.

Using it from code

Copy a provider's URL and use it as the base URL. With the OpenAI SDK for Python:

from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8787/p/<id>/",
    api_key="not-used",  # KeyRotator puts a real key here
)
print(client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Say hi"}],
).choices[0].message.content)
